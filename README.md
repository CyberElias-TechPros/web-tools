# Web Tools

**79 fast, private, in-browser utilities** — no uploads, no accounts, no tracking, no backend.

Every tool is a pure client-side computation. Your documents, PDFs, spreadsheets, images,
text and filenames never leave the tab they were dropped into. Combine Word files into a
PDF, merge or split PDFs, convert Excel to JSON, compress images, generate QR codes,
format SQL — all of it runs on your device.

## Architecture

**This project is a single static frontend. There is deliberately no backend.**

Every one of the 79 tools is a pure function of its input:

* nothing is persisted anywhere but the user's own `localStorage`,
* there is no user identity, so there is nothing to authenticate,
* there is no shared or multi-user state, so there is nothing to store,
* there is no third-party API to proxy, so there is nothing to keep a secret for.

Adding a database, an auth provider or an edge worker would add attack surface, latency,
cost and operational burden while removing the product's single most valuable property —
that your data physically cannot leave your device. The correct architecture for this
product is a static bundle on a CDN, and that is what it is.

```
index.html            pre-paint theme script, SEO/OG/JSON-LD metadata
  └── src/main.tsx    StrictMode → BrowserRouter → ThemeProvider → App
        └── App.tsx   MotionProvider + routes; every tool is React.lazy + Suspense
              ├── components/   Layout (header, ⌘K palette, footer), ToolShell, Dropzone,
              │                 PdfResult, TextIO, motion primitives, ui.tsx primitives
              ├── pages/        Home, About, Privacy, NotFound
              ├── tools/        registry.ts (metadata) + loaders.ts (lazy routes) + one folder per tool
              ├── hooks/        useLocalStorage, useDebounced, useCopy, useDropZone, useHotkey, …
              └── lib/          50+ framework-free modules — all the actual logic
```

The `src/lib/` layer contains no React code, which is why it can be tested exhaustively in
isolation. Almost all of it is first-party:

| Module | What it replaces |
|--------|------------------|
| `zip.ts` / `zip-reader.ts` | ZIP writer (platform `CompressionStream`) and a full ZIP/DEFLATE reader — not JSZip. |
| `docx.ts`, `xlsx.ts`, `pptx.ts` | OOXML parsers for Word, Excel and PowerPoint built on the ZIP reader + DOMParser — not mammoth or SheetJS. |
| `richdoc.ts`, `pdf-doc.ts` | A neutral document model and a paginating PDF layout engine (headings, lists, tables, images, links) on top of pdf-lib. |
| `md-parse.ts`, `markdown.ts` | Markdown → document model / clean text — not marked or remark. |
| `diff.ts` | Myers O(ND) diff with an edit-distance ceiling — not jsdiff. |
| `regex.ts` | Recursive-descent regex parser producing a span-annotated AST. |
| `csv.ts` | RFC 4180 parser with delimiter detection — not PapaParse. |
| `hash.ts`, `password.ts`, `textcrypto.ts` | MD5/CRC32 in TypeScript, Web Crypto for SHA/HMAC/AES-GCM/PBKDF2, CSPRNG everywhere. |
| `canvas.ts`, `image.ts`, `ico.ts`, `palette.ts`, `exif.ts` | Image decode/encode/resize, ICO writer, colour quantisation and EXIF/IPTC/XMP parsing. |

A handful of battle-tested client-side libraries are used where hand-rolling would risk
correctness rather than improve it:

| Dependency | Used for | Loaded |
|------------|----------|--------|
| `pdf-lib` | Writing and editing PDFs (merge, split, watermark, images → PDF, DOCX → PDF). | Only by PDF tools. |
| `pdfjs-dist` | Reading PDFs: rendering pages, thumbnails and text extraction. Worker served from this origin. | Only by PDF tools. |
| `yaml`, `sql-formatter`, `uqr` | YAML parsing, SQL formatting, QR matrix generation. | Only by their tool. |
| `motion` | Page transitions and micro-interactions (`LazyMotion`, features loaded async). | Shell. |
| `react`, `react-dom`, `react-router-dom`, `lucide-react`, `@fontsource-variable/*` | UI, routing, icons, self-hosted fonts. | Shell. |

Nothing is fetched from a third-party origin at runtime.

## Getting started

```bash
npm ci
npm run dev        # http://localhost:5173
```

| Script | Purpose |
|--------|---------|
| `npm run dev` | Vite dev server with HMR. |
| `npm run build` | Type-check the whole project, then produce `dist/`. |
| `npm run preview` | Serve the production build locally. |
| `npm test` | Run the full Vitest suite once. |
| `npm run test:watch` | Watch mode. |
| `npm run test:coverage` | Suite + V8 coverage of `src/lib/**`. |
| `npm run typecheck` | `tsc -b --noEmit`. |
| `npm run lint` | ESLint with type-aware rules. |

Requires Node 20.19+ (Vite 8).

### Adding a tool

1. Put the logic in `src/lib/<name>.ts` with a `<name>.test.ts` next to it.
2. Create `src/tools/<dir>/<Name>Tool.tsx`, default-exported and wrapped in `<ToolShell slug="…">`
   (the shell owns the page's single `<h1>`, title and meta description).
3. Register metadata in `src/tools/registry.ts` and the lazy import in `src/tools/loaders.ts`.
4. Add the route to `public/sitemap.xml`.

The integration and accessibility suites iterate over the registry, so a new tool is
automatically checked for a working lazy route, a single `<h1>`, no skipped heading levels,
labelled controls and a document title.

## Testing

The suite is 1,265 tests across 18 files:

* **Unit tests** for the `src/lib/` modules — parser edge cases, hostile input, RFC
  conformance (CRC-32 vectors, ZIP local headers, iCalendar line folding), real `.docx` /
  `.xlsx` / `.pptx` fixtures, PDF rendering round-trips through pdf-lib, DST and half-hour time
  zones, formula-injection escaping, path traversal and CSPRNG behaviour.
* **Integration tests** (`src/app.test.tsx`) that mount the real router and assert every one
  of the 79 tool routes lazy-loads and renders, the home page links to all of them, the 404
  path works, and the ⌘K palette filters, navigates and closes.
* **Structural accessibility tests** (`src/a11y.test.tsx`) that render every route and assert
  exactly one `<h1>`, no skipped heading levels, an accessible name on every button, link
  and form control, decorative SVG hidden from assistive technology, and a document title.
* **Interaction tests** (`src/tools/tools.test.tsx`) that drive tools through
  `@testing-library/user-event`.

Canvas encoding and pdf.js rendering are not implemented in jsdom, so those pixel pipelines
are verified in a real browser; their pure helpers are unit-tested.

## Deploying to Vercel

The repository is Vercel-ready; `vercel.json` sets the framework, the SPA rewrite and all
response headers.

**Via the dashboard**

1. Import the Git repository at <https://vercel.com/new>.
2. Framework preset: **Vite** (detected automatically).
3. Build command `npm run build`, output directory `dist`, install command `npm ci` — all
   already declared in `vercel.json`.
4. No environment variables are required. There are none.
5. Deploy.

**Via the CLI**

```bash
npm i -g vercel
vercel          # preview deployment
vercel --prod   # production
```

**After the first deploy**, replace the placeholder origin `https://web-tools.vercel.app`
with your real domain in three places, so canonical URLs and social previews are correct:

* `index.html` — `<link rel="canonical">`, `og:url`, `og:image`, `twitter:image`, JSON-LD `url`
* `public/robots.txt` — the `Sitemap:` line
* `public/sitemap.xml` — every `<loc>`

`vercel.json` handles the two things a static SPA always gets wrong:

* **Deep links.** Every path that is not a real file rewrites to `/index.html`, so
  `/tools/pdf-merge` returns 200 on a cold load instead of 404.
* **Caching.** Content-hashed files under `/assets/` get `immutable, max-age=31536000`;
  `index.html` gets `must-revalidate`, so a new deploy is picked up on the next navigation.

## Security

* **No network egress.** No `fetch`, no `XMLHttpRequest`, no WebSocket, no analytics, no
  fonts or scripts from a CDN. The Content-Security-Policy pins `connect-src` to `'self'`,
  so any accidental future call to a third party fails loudly in the browser.
* **CSP**: `object-src 'none'`, `frame-ancestors 'none'`, `base-uri 'self'`,
  `form-action 'self'`, `upgrade-insecure-requests`. `worker-src` and `frame-src` allow
  `blob:` for the same-origin pdf.js worker and the inline PDF previews.
* **Generated HTML is escaped.** The only `dangerouslySetInnerHTML` is the Markdown → PDF live
  preview, fed exclusively by our own serialiser, which escapes all text and attribute values
  and drops `javascript:` and other unsafe URL schemes. Imported HTML never executes: it is
  parsed with `DOMParser` into a document model, and scripts, styles and remote images are
  discarded.
* **Office files are parsed, not executed.** DOCX/XLSX/PPTX are unzipped in memory with a
  first-party, bounds-checked reader (nothing is ever written to disk under an archive's own
  file names — downloads go through `safeFilename`); XML is parsed with `DOMParser`, which
  resolves no external entities. Only images embedded in the file are ever read.
* **No `eval`, no `new Function`.** The JSON path query is a hand-written token walker that
  only reads *own* properties.
* **CSV formula injection** is neutralised on export: any field starting with `=`, `+`,
  `-`, `@`, tab or CR is prefixed with `'`.
* **Path traversal** is impossible in file-producing tools: `sanitizeZipPath` and
  `safeFilename` strip separators and `..` segments and reject Windows device names.
* **Passwords and keys** come only from `crypto.getRandomValues` with rejection sampling; AES
  uses 256-bit GCM with PBKDF2-SHA-256 (600 000 iterations) and a fresh salt and nonce.
* **Denial-of-service ceilings** are explicit: regex match and time budgets, diff
  edit-distance ceilings, image megapixel limits, text-file size limits and ZIP entry limits.

## Accessibility

Semantic landmarks, a skip link, visible focus rings, real `<label>` associations,
`aria-live` regions for copy feedback and generated results, `aria-modal` dialogs with Escape
handling and focus management, keyboard-operable custom controls (including the PDF page
organiser), `prefers-reduced-motion` support that disables all decorative motion, and light
and dark themes that follow the system setting until overridden.

## Performance

* Every tool is a separate lazy chunk; the home page loads none of them.
* Heavy libraries (pdf.js, pdf-lib, sql-formatter, yaml) are split into their own chunks and
  only download with the first tool that needs them. The pdf.js worker is a separate asset.
* Expensive computations are debounced and memoised; image and PDF work runs sequentially
  with progress so memory stays bounded on mobile browsers.
* Object URLs are revoked, `ImageBitmap`s are closed, and canvases are released after every
  operation.

## Privacy

There is no analytics, no telemetry, no error reporting service, no cookies and no
fingerprinting. The only thing stored is your own tool preferences, in `localStorage`.
Clearing site data removes all of it. See `/privacy`.
